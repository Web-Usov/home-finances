# 99. Открытые решения

> **Назначение файла:** решения, которые нужно принять до публикации. Отложенные функции («Вне MVP») перечислены в [00-scope.md](00-scope.md) (SCOPE-16…SCOPE-22).
> **Префикс ID:** `Q`.

## Решения до публикации

- **[Q-01]** выбрать место размещения: домашний сервер либо облако;

- **[Q-02]** если доступ будет не только из приватной сети — добавить встроенную авторизацию или обязательную внешнюю защиту;

- **[Q-03]** утвердить название продукта, визуальную тему и домен; эти решения не меняют финансовую модель и API-контракт.

- **[Q-04]** единая форма ответа мутаций месяца. Сейчас `PATCH /months/{period}` (API-03) возвращает `data` = краткую сводку месяца (`MonthSummary`), `POST /operations` (API-10) — `data: { operation, result, summary }`, `PUT .../allocations` (API-04) — `data` = полную сводку с остатками конвертов. Варианты: (A) оставить как есть и описать каждый ответ отдельно; (B) все мутации месяца возвращают `data.summary` одной формы (`MonthSummary`: id, period, status, income, version, распределено, свободно), а остатки конвертов клиент берёт из `GET /api/dashboard/monthly` (API-12) — один запрос после мутации; (C) все мутации возвращают полную сводку с остатками конвертов. Рекомендация планировщика — B: клиентский код и сгенерированные типы единообразны, тело мутации не раздувается, а дашборд всё равно перезапрашивается. Последствие B — изменение контракта `PATCH /months` и `PUT .../allocations` (задача T-027 блокируется этим вопросом; затрагивает UI-задачу T-010). Правило в `docs/spec` будет добавлено после решения (следующий свободный номер API).

> **Итог версии 1.0.** Требования финансовой логики, операций, закрытия месяцев, интерфейса и приёмки зафиксированы. Неопределённым остаётся только способ размещения и связанная с ним защита доступа.
