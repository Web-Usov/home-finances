# 0004. Расчётный движок без состояния, внешний tx, каскадный пересчёт в одной транзакции

## Статус

Принято (2026-08-15). Действует.

## Контекст

Любое изменение исходных данных должно пересчитывать все последующие месяцы, а пользователь не должен видеть промежуточных остатков (CALC-13, API-15, NFR-16). Движок не должен зависеть от UI и контроллеров, обязан быть детерминированным и тестируемым (CALC-14). Модули Months/Envelopes/Allocations/Operations меняют исходные данные и должны фиксировать их вместе с пересчётом атомарно.

## Решение

- `CalculationEngineService` (`apps/api/src/modules/calculation-engine/`) не хранит состояния между вызовами; единственная зависимость — `PrismaService`. HTTP-логики в нём нет.
- Исходные данные (Operation, Allocation, доходы) движок не изменяет; он удаляет и пересоздаёт только производные записи (`OperationResult`, `EnvelopeMonthSnapshot`).
- Публичный API: `recalculateFrom(period, db?)` и `recalculateMonthAtomically(monthId, db?)`. Если передан внешний tx-клиент `db`, пересчёт выполняется внутри него; иначе движок сам открывает `$transaction`.
- Вызывающий сервис открывает `prisma.$transaction`, записывает исходные данные и вызывает движок с тем же tx — изменение и каскад коммитятся атомарно.
- Каскад пересчитывает все месяцы от затронутого вперёд и увеличивает `version` у затронутых `BudgetMonth` (см. 0005).

## Последствия

- Формулы покрываются модульными тестами без БД; интеграционные тесты проверяют транзакционность.
- Сервисы обязаны передавать tx в движок; вызов движка вне транзакции мутации нарушает атомарность.
- Полный пересчёт — единственный способ получить производные данные, поэтому он должен укладываться в бюджеты NFR-14 / NFR-15.
- Порядок внедрения «движок первым» (core-first) зафиксирован в `docs/archive/omo/drafts/domain-modules-impl.md`: остальные модули делегируют расчёты движку.
