# 0013. Поставка: один compose-стек и веб-контейнер на том же origin

## Статус

Предложено (2026-11-01). Принимается мержем PR.

## Контекст

Задача T-016 добавила запуск «с нуля» через `docker compose up`: PostgreSQL, одноразовая миграция, API и веб-клиент. Нужно было выбрать, как отдавать клиент и как он обращается к API (AC-22, DOD-01). Решение принято при реализации и до сих пор нигде не зафиксировано.

## Решение

- Поставка — один compose-стек: `postgres` → `migrate` (одноразовый `prisma migrate deploy`) → `api` → `web`.
- `web` — статический экспорт Expo (`expo export --platform web`, `EXPO_PUBLIC_API_URL=same-origin`), который раздаёт существующий `scripts/preview/serve-web.mjs` (SPA-fallback, прокси `/api` на сервис `api`). Тот же скрипт использует превью владельца (`docs/preview.md`).
- Клиент и API живут на одном origin, поэтому CORS не настраивается; отдельный nginx (или другой reverse proxy) не добавляется.
- Наружу публикуется один порт веба; порты хоста настраиваются переменными окружения.

## Последствия

- Нет нового инструмента и конфигурации: поведение в compose и в превью совпадает.
- Прокси в `serve-web.mjs` — часть поставки; нужны HTTPS, кэширование или балансировка — вернуться к вопросу новым ADR.
- Архитектура приложения (API, клиент, БД) не меняется; ADR фиксирует только топологию поставки.
- Заголовки CORS из API-26 нужны только для dev-режима (клиент на другом порту), в compose не используются.
