# Эпики

Эпик — крупный кусок ценности для пользователя, который закрывается **вехой (milestone)**. Эпики пишутся по-русски и предназначены для владельца продукта; детальные задачи для агентов (на английском) лежат в [`../tasks/`](../tasks/README.md).

## Формат файла

Файл `E-NN-slug.md`, во frontmatter:

```yaml
---
id: E-01
title: Ядро API: месяцы и операции
status: planned        # planned | in_progress | done | accepted
accepted: null         # дата приёмки YYYY-MM-DD или null
spec: [MON-05, OP-05]  # идентификаторы правил спецификации (docs/spec/**)
---
```

Разделы тела: «Ценность для пользователя», «Ключевые фичи», «Охват правил спеки», «Критерии приёмки вехи», «Вне охвата», «Задачи».

## Статусы и приёмка вехи

- `planned` — работа не начата; `in_progress` — есть начатые задачи.
- `done` — все задачи эпика выполнены (PR смёржены, CI зелёный). Статус ставит агент/оркестратор.
- `accepted` — **веху принимает человек** (владелец). Только владелец вписывает во frontmatter `accepted: YYYY-MM-DD` и меняет статус на `accepted`, пройдя раздел «Критерии приёмки вехи» (демо-сценарий, список AC, скриншоты e2e). Агенты это поле не заполняют.
- Если приёмка выявила проблемы, владелец возвращает статус `in_progress`, а доработки оформляются новыми задачами.

## Доска задач

Список задач эпика ведётся автоматически: [`../tasks/README.md`](../tasks/README.md) генерируется командой `node scripts/tasks.mjs board` и сгруппирован по эпикам. В файлах эпиков список задач вручную **не** ведётся.

## Правила

- Правила спецификации указываются только по ID (`OP-05`), существование ID проверяет `scripts/spec-check.mjs`.
- Изменения в `epics/**` требуют ревью владельца (CODEOWNERS).
